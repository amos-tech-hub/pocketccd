# 自定义配方与批量重调：可行性拆解

日期：2026-11-15
状态：**仅分析，未改代码。** 本文回答"要不要做、怎么做、代价多大"，不包含实现。

---

## 1. 需求从哪来

用户今天只能"拍之前选机身"。拍完或导入之后想换风格，只能重拍一遍。由此拆出三个需求，它们的成本差了一个数量级，不能捆在一起谈：

| 编号 | 需求 | 用户说法 |
| --- | --- | --- |
| R1 | 重新冲洗单张 | "这张用 A8 再出一次" |
| R2 | 整卷换风格 | "这一卷都想换成 N2" |
| R3 | 保存自己的微调 | "我把颗粒推满了，存成我的 A8" |

## 2. 现状核查（代码事实）

| 事实 | 位置 | 后果 |
| --- | --- | --- |
| 21 个调色参数是 `private var`，绑定在 enum case 上 | `CCDLook.swift` 的 `processed()` 与参数段 | 没有"配方"这个数据结构，R3 无法直接实现 |
| 相册只存渲染后的 JPEG | `MemoryFeatures.swift` `RollStore.add` → `image.jpegData` | 没有原片，R2 无法无损重做（重调＝二次上色） |
| `RollEntry` 只记 `cameraRawValue` / `mode` / `qualityScore` / `note` | `MemoryFeatures.swift:6` | 没有配方快照，历史照片无法知道"当时怎么调的" |
| 导入照片每次从相册读原图 | `CameraScreen.swift` `importPhoto` | R1 对"导入的照片"天然可行，零新增存储 |
| 没有任何配方/预设存储 | 全仓搜索无命中 | 从零开始 |
| 产品规格明确反对预设泛滥 | `docs/PRODUCT_SPEC.md:33`："A few recognizable cameras are better than hundreds of presets" | 自定义配方必须限量，否则与产品定位冲突 |

## 3. 三个结构性障碍

### 障碍一：没有原片，就没有批量重调

调色链是有损的：`whiteClamp` 截断高光、`CIBloom` 不可逆、`shadowLift` 抬过的暗部回不来。对已渲染的 JPEG 再跑一遍 `CCDLook.render`，得到的是"上了两次色"的图，不是"换了一台机身"的图。

要让 R2 成立，只有两条路：

- **存原片**：拍照时多写一份未调色的 JPEG；
- **每次回相册重取**：只对"导入的照片"可行（原始文件在 Photos 里）；自己拍的照片，原片一旦丢弃就找不回来。

### 障碍二：`CCDLook` 不是配方，是写死的机身

参数全部是 `private var`，从 `self` 推导。要做 R3，必须先把这些参数提成一个值类型（`LookRecipe`），再让 `CCDLook` 变成"预设值 + 可选覆盖"。这是**机械但面积很大**的重构：约 30 个数值、渲染管线入口 `render/livePreview/videoFrame` 三处，以及 `ProductInfrastructureTests` 里"白卡不截断 / 灰卡 R-B / 四种机身成片互异"这些端到端断言。

### 障碍三：产品哲学与"预设"这个词冲突

规格写的是"少而可识别"，竞品的失败恰好是"上百个滤镜"。所以要做的不是"预设中心"，而是**"给一台机身做一点点个人偏移"**——参数轴必须收敛到 3–4 个感知维度，不能把 21 个参数摊开。

## 4. 数据模型提案

### 4.1 `LookRecipe`（值类型，替代写死的参数表）

```swift
struct LookRecipe: Equatable, Sendable {
    // 与 CCDLook 现有参数一一对应，保持像素级一致
    var shadowLift, sharpening, contrast, saturation: Double
    var temperature, tint: CGFloat
    var grain, bloomIntensity, bloomRadius: Double
    var whiteClamp, blackClamp: CGFloat
    // …其余字段照搬，toneCurve 用 [[CGFloat]] 或 5 组点
}
```

`CCDLook` 改为 `var recipe: LookRecipe { LookRecipe.amber / .party / .chrome / .night }`，渲染路径只认 `recipe`。**这一步做完，行为必须逐像素不变**——用现有的 `ProductInfrastructureTests` 白卡/灰卡/配方互异三个用例当回归闸门。

### 4.2 `UserRecipe`（用户配方）

```swift
struct UserRecipe: Codable, Identifiable {
    let id: UUID
    var name: String
    var baseLook: String        // CCDLook.rawValue
    var axes: [String: Double]  // 只允许 4 个轴，0…1 归一化
}
```

四个轴（其余不开）：`grain`（颗粒）、`flashDecay`（闪光衰减硬度）、`warmth`（色温偏移 ±）、`contrast`。每个轴映射到有界的参数区间，保证"推满也不会坏"。

**上限 3 个配方**。超了就要求删——这不是技术限制，是产品定位限制。

## 5. 两条路线（这是本文最需要拍板的地方）

| | 路线 A：只做"导入照片"的批量 | 路线 B：存原片，全量重调 |
| --- | --- | --- |
| 覆盖 | 相册里已有的照片；自己拍的看不到原片 | 自己拍的 + 导入的 |
| 存储成本 | **0** | 每张 +3–9 MB（实测样张 3.4–9.0 MB，均值 5.8 MB）；24 张一卷 ≈ **140 MB** |
| 需要改的模块 | 导入流程 + 结果页（新增"换机身重冲"） | `CameraController` 落盘、`RollStore` 双文件、缩略图缓存失效、归档策略 |
| 风险 | 低，纯增量 | 中：磁盘、卷开发时的清理、备份/恢复格式 |
| 能否撑起付费 | 弱（一次性的小工具） | 强（"整卷重洗"是真需求） |

路线 B 的一个折中：**只在"当前卷"保留原片，卷开发（develop）时删掉**。存储上限被卷容量（12/24）锁定，不会无限膨胀；代价是归档卷不能重调——这与"冲洗完就是成品"的产品叙事一致。

## 6. 入口与命名（避免变成参数 App）

| 场景 | 入口 | 文案 |
| --- | --- | --- |
| 单张重冲（导入） | 结果页 `···` → Re-develop | "用另一台机身重冲" |
| 整卷重调 | 相册 `···` → Develop again | "整卷换机身"（仅当原片存在） |
| 保存配方 | 仅在"调过 4 个轴"之后出现 | "存为我的配方" |

**不做**：配方商店、配方分享、导入他人配方、21 参数全开放。

## 7. 付费边界（先功能后收费）

按上一轮结论：功能不存在时不写进付费页。功能做完之后，可付费的候选只有两个，且都应该是"效率"而不是"能力"：

- 整卷批量重调（批量，不是单张）；
- 保存配方（数量上限：免费 1 个 / 付费 3 个）。

**保持免费**：单张导入重冲（这是"先试后买"的最短路径）、导出与分享。

## 8. 分阶段实施

| 阶段 | 内容 | 依赖 | 可独立验收 |
| --- | --- | --- | --- |
| P0 | 抽取 `LookRecipe`，机身行为逐像素不变 | 无 | 是（现有测试全绿 + 白卡峰值不变） |
| P1 | 单张"换机身重冲"（导入路径复用） | P0 | 是 |
| P2 | 存原片（仅当前卷）+ 整卷重调 | P0、P1 | 是 |
| P3 | 四轴微调 + 保存配方（上限 3） | P0 | 是 |

P0 是纯重构，风险最低但面积最大；建议单独一个 PR，不带任何新 UI。

## 9. 验收与回归点

- P0：`ProductInfrastructureTests` 全绿；白卡峰值、灰卡 R/B、四机身 JPEG 哈希互异三项与改动前逐项对照（像素峰值容差 ≤ 1/255）。
- P1：同一张原图，从 A7 切到 A8 重冲，输出与"直接用 A8 拍"的链路一致（同一 `render` 参数）。
- P2：卷开发后原片被删除；归档卷重调的入口不出现；备份/恢复不因多一个文件而失败。
- P3：配方跨启动保持；配方数上限生效；配方作用后仍通过白卡不截断。
