# 这两个库还能给 Pocket CCD 什么：工程经验清单

日期 2026-11-19。除 3D LUT 外，从 SpektraLab / Silverphase 提炼的可迁移经验。
每条给：**他们怎么做 → 我们对应的问题 → 可执行动作**。未改代码。

## 0. 如果只抄三件事

1. **颜色 bug 是静默的，测试要测"不变性"而不是参考图**（他们 750 个测试全绿时同时有 3 个颜色 bug）。
2. **性能先拆子步骤再下结论**（一次 45 MP 的 7 秒藏在 `rescale` 里，不是 GPU 问题）。
3. **预览与成片必须同源**（他们的相机预览与完整渲染差 ≤1/65535；我们今晚的肤色问题正是"预览看着行、成片不行"）。

## 1. 性能与内存

**他们踩过的三个"慢"（trap 18）**
- Frame arena 不回收：45 MP 一次渲染驻留 3.2 GB、6.4 s；改成引用计数后 0.4 s。
- setup cache 没移植：每次拖滑块重算 C_max 表和 192×192×81 tc_lut，160–250 ms。
- open 路径全帧拷贝：24 MP RAW 打开 5.9 s → 2.0 s。
- 方法：先确认 `core=native-metal`，再分 tier 计时，最后看**重复渲染的峰值内存**——池子在涨就是线索。

**分级 tier + 缓存**
- live 1600 px 0.13 s / preview 3400 px 0.25 s / full 7800×5800 0.87 s；切相纸 LUT 2 / 9.5 / 47 ms。
- 相机端：latest-only mailbox（只保留最新帧，慢就丢帧、不排队）；cube 缓存 2 个 LRU；低电量**只降分辨率/帧率，不降 look**。

**对应 Pocket CCD**
- 今晚量到预览 20.6 ms/帧、人脸 160→85 ms；下一步不是换渲染器，而是查：每帧是否重复分配 CIImage/CIContext、回调是否重复注册、预览是否走了成片的整条链。
- 我们已经有"降分辨率不降画质"的正确动作（人脸 1280 px），继续沿用到缩略图/相册。

## 2. 颜色（最值钱的部分）

**trap 11：颜色 bug 是静默的，均匀偏置的测试会报满信心**
- 2026-08-26 同时 3 个颜色 bug、750 测试通过：编码/解码路径不一致、gain 乘进了 gamma 数据（等效 `g**1.8`）。都不崩，两张还"看起来像照片"。
- 原因：**所有测试输入都是线性的**，而用户实际给的是编码整数文件。测试不是弱，是**方向单一**。
- 对应我们：89 个测试全过，但四台相机仍集体脸红——测试都在同一类输入/同一场景上。补**不变性测试**：同一颜色用不同表示（P3/sRGB、8/16 bit、RAW/JPEG）→ 渲染应一致。

**trap 8：二阶矩对，观感仍会变**
- `fast_stats` 把颗粒 RMS 误差做到 0.14%，但把 skewness 全部抹平；而 skewness 编码了"暗部颗粒 vs 高光颗粒"的性格。
- 对应我们：颗粒遮罩改 `f(L)=0.2+3.2L-3.2L²` 时，正是只看了均值/强度，没看分布形状。**颗粒模型至少要校验均值、方差、偏度三阶**，或直接和真机样张做 PSD。

**trap 31：颜色死在 toe，比影调死得早**
- 同一色度在不同曝光下：肤色 C\*ab 在 −3.5 EV 以下≈1.7（变灰），色彩窗口 4.2–4.4 档，而影调窗口 5.66 档。
- 对应我们：N2 暗部"死黑"、阴影里肤色发灰。**暗部恢复只能救影调，救不回颜色**——这是物理限制，产品文案别承诺"暗部也能出肤色"。

**trap 12：输入契约才是产品崩的地方**
- 解码必须在门口做一次，下游全线性；外部 RAW 编辑器的曝光不是 gain（有曲线时 +1 EV 实测 ×1.57、跨影调 1.8–2.1×）；外部解码不可逆。
- 对应我们：现在吃 BGRA/sRGB（已 tone-map），所以 LUT 不需要 shaper；但一旦接 ProRAW，必须先把"输入是什么、在哪解码"写死，否则就是他们那张"正确但倒置的照片"。

**trap 27：每个到 drawable 的字面量都要在工作空间**
- 画布从 P3 换到 ProPhoto 后，同一个 `0x5F` 字面量亮度变成 1.478×，整个 UI 跟着照片一起偏。
- 对应我们：结果页/相册/分享图的背景色、遮罩色、导出 P3/sRGB 的转换，应有"两条路径落到同一像素"的检查（他们用窗口边距 95 vs 95.03 做裁判）。

## 3. 测试纪律

- **trap 26：skip 的套件和全量套件都报 0 failures**。他们 18 s/25 skipped 与 375 s/0 skipped 都"绿"，被跳过的正是两个关键测量。**看时长和用例数，不看失败数**。我们 89 tests 要记录实际执行数与耗时，别让"缺 fixture 就跳过"变成假绿。
- **trap 23：绿色 parity 不是正确图**。两个真 bug（上下翻转、纹理提前释放）在 27/27 绿的 harness 之外。**要看快照**。我们的 UI 测试截图正是这个角色——保留并扩大。
- **测试拥有自己的输入**：注入 UserDefaults suite、复制 fixture 再打开、不读共享存储。
- **先红后绿**：新增回归测试必须先看到它失败，再修。
- **错误信息要说"可用的选项"**：未知 stock 报错时列出可用的 8 个；我们也该在"相机不可用/文件缺失"时报清可用项。

## 4. 输入/输出契约（产品层）

- 预览与成片**同源**：他们的相机 LUT 路径与完整引擎逐像素差 ≤1 count（18 组 film×metering 交叉验证）。我们做 3D LUT 时，这就是验收标准。
- 导出配方化：格式/色彩空间/尺寸/命名规则/是否嵌预览，全部是可保存的 recipe；批量导出要注意"当前打开的帧"（trap 34：exporter 写的是打开的那张）。
- DI 导出把"文件 + 视图 LUT"作为一个包，`.cube` 与文件同源，避免两套实现漂移。

## 5. 工程/构建

- **工程文件由脚本生成**：`gen-project.py --check` 保证 xcodeproj 与源文件一致；手工加文件会得到 "cannot find X in scope" 或链接错误。我们的 PocketCCD.xcodeproj 是手改的，新增文件容易漂。
- **资源打包校验**：`check-bundle-resources.sh` + 哈希/UPSTREAM.json + 许可打包脚本；资源缺失是"明确报错"而不是静默降级。
- **构建缓存按源文件/头文件/编译器哈希**，避免"改了引擎没重编"的假象。
- **模拟器不证明真机**：触控、内存 entitlement、全分辨率导出都要真机单独验。我们已经有真机取数习惯，保持。
- **已知限制写进文档**（Camera Control 认证前不可用、Duo RAW 黑图），而不是等用户发现。

## 6. 产品/UX

- **三档预览**：system（无效果）/ approximate（LUT）/ native（引擎），命名诚实；近似模式明确标注"approximate"。
- **低电量策略只降分辨率与帧率，不降 look**——观感一致优先于流畅。
- **专业出口**：Cineon DI + 双视图 LUT、16-bit TIFF，给调色用户；我们目前只有 JPEG/PNG，若做付费专业版可参考。
- **对比/参考**：他们的 Light Table、双照片半格、软打样——都是"让用户相信自己看到的是对的"的功能。

## 7. 对 Pocket CCD 的优先级（现在就能做）

1. **给颜色测试加"不变性"维度**：P3/sRGB、8/16-bit、RAW/JPEG 同色渲染一致（半天）。
2. **颗粒模型加三阶校验**（均值/方差/偏度），或直接对真机样张做 PSD（半天）。
3. **预览/成片一致性测试**：同一帧走预览路径与成片路径，逐像素差 ≤1–2 count（1 天，和 3D LUT 一起做）。
4. **性能拆子步骤**：给 `processed()` 每一段打点（curve / lumaContrast / grain / shoulder / lens），先找最大头，别再整体猜（半天）。
5. **测试报告加"执行数/跳过数/耗时"**，防止假绿（十分钟）。

## 8. 一句话

他们的价值不在"另一个相机 App 的代码"，而在**一套把"看起来对"变成"量出来对"的纪律**：输入契约、不变性测试、三阶统计、tier 计时、同源导出。Pocket CCD 下一步最该抄的是这套纪律，不是他们的滤镜。
