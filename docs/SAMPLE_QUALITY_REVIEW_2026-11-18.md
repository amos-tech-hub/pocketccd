# 真机样张质量分析（2026-11-18）

样本：Adam 的 iPhone 16 Plus 上 PocketCCD 当前胶卷 24 张成片 + 12 组原始帧（36 帧）
取回方式：`xcrun devicectl device copy from --domain-type appDataContainer`
分析工具：`Research/originals_report.swift`（原始帧门槛）+ 自写 numpy 指标（成片）
原始文件：`/tmp/pccd-samples/`（不入库）；可视对比：`.tmp/phone-samples/`

---

## 0. 结论先行

1. **P0 方向 bug**：13 张带「旋转 90°」EXIF 标记，全部来自 **Flash Sequence**。竖着拍碰巧正确，横着拍就是歪的——发给朋友、进相册、进微信都歪。
2. **A7 人脸过红**：自拍肤色 R/G = **2.04**（红通道是绿的两倍），唇色被打成荧光红；序列帧 1.37–1.77。
3. **N2 基本不可用**：两张平均亮度 0.16，一张几乎全黑（luma 0.10、零高光裁切），看不出内容。
4. **颗粒过重**：暗部拉普拉斯噪声 5.7–6.9，A7 黄昏序列最高 **10.8**，放大即糊。
5. **白平衡在两个方向都越界**：A7 黄昏全幅 R/B **0.64–0.90**（偏蓝），A8 街景 **1.68–1.70**（偏红），产品自己的门槛是 1.15–1.35。
6. 结论：**这批样张不能直接当商店截图**。可用的只有 A8 / C1 室内自拍（2 张）。

## 4. 六个问题与证据

### P0 · 照片方向（2026-11-18 定稿，真机已验）

四次迭代，前三次都错，把有效的线索记下来：

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | 看像素认定标记错，横持丢标记 | 用 `UIDevice.orientation` 判向，首拍常是 `.unknown` → 静默走竖屏分支，等于没修 |
| 2 | 一律把标记烘进像素 | 把错误的标记固化了，横拍得到「竖图 + 躺着的内容」 |
| 3 | 重力判横竖，横持丢标记 | 横拍仍差 **180°** |
| 4 | 横持再分两侧，一侧 0°、一侧 180° | **真机通过** |

关键事实（都是真机文件里量出来的，不是推断）：

- 原始帧永远是 `4032×3024 + orientation 6`，但像素朝向随握法变；
- 两个横持方向的 buffer 相差 180°：一个已经正，一个上下颠倒；
- `UIDevice.orientation` 有预热期，第一拍不可信；
- 竖持时标记 6 是对的，横持时它是错的。

最终规则（`CaptureTilt` + `UIImage.exportReady()`）：

```
竖持                      → 把标记烘进像素（保留 .up）
横持 · gravity.x > 0      → 先转 180°，再丢标记
横持 · gravity.x < 0      → 丢标记
无加速度样本              → 退回竖持分支
```

`|x| > |y| + 0.2` 的阈值防手抖；加速度计无需权限、无预热。

验证：22:11 那张横拍成片为 `4032×3024 + orientation 1`，像素里笔记本正立、标签文字可读，用户确认「对了」。测试 `ExportOrientationTests` 5 条（横持两侧、竖持烘标记、重力判向、已正立零重绘），全仓 71 tests / 21 suites 通过。

DEBUG 构建会把 `x / y / landscape / turns` 写进 `debug.lastOrientation`，下次换机型（传感器安装方向可能不同）时可直接读出来定映射，不必再猜。

### P1 · A7 人脸红得过头（2026-11-18 已修，待真机看片）

**病因**：A7 的暖调曲线在闪光下人脸上把红通道推到先于亮度饱和，唇部直接顶到 255，于是出现荧光唇、橘红脸颊。真机成片上量到的红色像素 R/G 是 **2.04**，产品门槛是 1.15–1.35。

**修法**：一个 32³ 颜色立方体（`redGuardCube`），只对 A7 生效，条件很窄——红通道必须是三通道里最亮的、且已经进入高光段（`smoothstep(0.30, 0.65, R)`），把「超出邻居的那部分红」按 0.9 的强度压回去，并给单像素设定 **0.24（线性）的削减上限**。上限是关键：没有它，路灯和夕阳会和皮肤一起被洗灰。

合成样片实测（渲染后 sRGB 均值）：

| 输入 | 修前 R/G | 修后 R/G |
|---|---:|---:|
| 闪光肤色（200,122,108） | 2.15 | **1.69** |
| 高光肤色（232,150,128） | 1.74 | **1.45** |
| 中性卡（200,200,200） | 1.04 | 1.03 |
| 钠灯（245,170,60） | 1.51 | 1.28 |
| 夕阳（240,150,90） | 1.80 | 1.51 |
| 唇色（190,40,50） | 8.42 | 6.45（R 202→164） |

取舍说明：肤色没有压到 1.35，是因为再压就轮到路灯变黄、夕阳发灰。先看真机片，如果脸还偏红，把 `redGuardLimit` 从 0.24 提到 0.30（夕阳会掉到 1.44、路灯 1.22）。

预览和成片走同一条 `processed()`，所以取景器里看到的就是存下来的。

测试：`A7RedGuardTests` 4 条（闪光肤色落在 1.30–1.85、路灯保持 >1.20、中性不变、A8 不受影响），全仓 75 tests / 22 suites 通过。

### P1 · N2 太暗（2026-11-18 第一版调整，待真机片确认）

**病因**：N2 同时叠了三个压暗项 —— `exposureEV -0.12`、`shadowLift -0.18`（把暗部再压下去）、以及一条在 0.25 处只给 0.14 的陡峭 toe。真机样张平均亮度 **0.16**、其中一张 0.10 且高光裁切 0%，画面里没有任何亮点。

**改动**：

| 参数 | 旧 | 新 |
|---|---:|---:|
| `exposureEV` | -0.12 | **+0.10** |
| `shadowLift` | -0.18 | **-0.02** |
| tone curve 0.25 点 | 0.14 | **0.19** |
| tone curve 0.5 点 | 0.45 | **0.50** |

预期：整体提 0.22 挡左右，暗部不再被主动压死，中灰上移，同时保留 0.008 的黑位锚与 0.945 的白点，不至于变成「发灰的夜景」。

**注意**：这一项没能在单测里定量验证——合成色块在测试环境里渲染出的亮度与输入不相关（三档输入得到完全相同的输出），说明在那条路径上测不出真实响应，所以这是一次基于参数的保守调整，**需要一张真的 N2 夜拍来验**。验收线：平均亮度 ≥0.20，p95 ≥0.55，黑位不塌成纯黑。

### P2 · 颗粒重到盖住细节（2026-11-18 第一版调整）

**真机复测（22:35 N2 夜景）**：暗部拉普拉斯噪声 **9.70**，而 11-15 那张几乎全黑的 N2 只有 3.52——因为噪声是按亮度跑的，提亮 24% 之后噪声一起显形了。同一批里 A7 室内自拍的噪声是 **13.93**，说明**大部分噪点来自高 ISO 的传感器本身，不是我们叠的合成颗粒**。

**改动**（两条同时做，只减颗粒会把传感器噪点原样留下）：

| 参数 | A7 | A8 | C1 | N2 |
|---|---:|---:|---:|---:|
| `grain` 旧 → 新 | 0.006 → **0.004** | 0.010 → **0.007** | 0.006 → **0.004** | 0.015 → **0.009** |
| `noiseReduction` 旧 → 新 | 0.014 → **0.020** | 0.016 → **0.024** | 0.010 → **0.014** | 0.022 → **0.034** |

取舍：降噪拉太满会让 CCD 的「脏」变成手机的「塑料」，所以 N2 只提到 0.034、保留 `noiseReductionSharpness 0.12` 的低锐化。目标是把暗部噪声压到 7 以下，同时不出现涂抹块。

### P2 · 白平衡跨场景漂移（2026-11-18 已加有界校正，待真机验）

**病因**：每台相机只有一组固定色温/色调（A7 5250/+6、A8 5150/+5…），场景一换就整片偏色：A7 黄昏 R/B **0.64**（很蓝），A8 钠灯街 **1.70**（很红），产品门槛是 1.15–1.35。

**修法：有界场景白平衡**（不做全自动，避免抹掉相机性格）。

- 每帧取一次 `CIAreaAverage`，算场景的红蓝比；
- 只在**极端**时介入：R/B > 1.60（偏红）或 < 1.05（偏蓝），中间留死区；
- 只动蓝通道，且**单通道最多 ±8%**（`blueGain` 夹在 0.92–1.08）；
- 预览帧的均值缓存 0.5 秒，避免 24fps 下每帧回读 GPU；成片始终重新测量。

效果（纯函数标定）：偏红场景把蓝抬到 +8% 上限，偏蓝场景把蓝压到 −8% 下限，中间地带完全不动。合成验证：极端红场景 R/B 4.86 → **3.69**，极端蓝场景 0.73 → **0.79**，中性场景仍落在 A7 的暖调区间（R/B 1.20，门槛内）。

取舍：8% 的幅度不足以把黄昏「洗成中性」，这是刻意的——A7 的身份就是暖；目标是「不再极端漂移」，不是「所有场景一个味」。

测试：`SceneWhiteBalanceTests` 4 条（红偏抬蓝并夹住上限、蓝偏压蓝并夹住下限、中性死区不动、A7 中性仍在其暖调区间），全仓 79 tests / 23 suites 通过。

### P2 · 序列三帧像三个场景

- 4 组里 ambient 与 flash 的亮度差 0.06–0.24，结果页并排看很割裂。

## 5. 修法（按顺序，前两项必须发货前做）

| 顺序 | 动作 | 落点 | 验证 |
|---|---|---|---|
| 1 | 写盘前把方向烘进像素、统一写 `orientation=1`；或按设备朝向设置 `videoOrientation` | `CameraController.captureSequence` / `CCDLook.render` / `MemoryStore.add` | 横竖各拍 5 张，相册里全部正立 |
| 2 | A7 肤色：红通道做亮部保护（R 通道在 >0.85 后压缩），唇色避免纯红饱和 | `CCDLook.processed` A7 分支、`lumaContrastCube` 后加肤色保护 | 自拍 R/G 落回 1.15–1.40 |
| 3 | N2 提亮暗部 0.5–0.8 EV，保留黑位但不许 0 高光 | N2 曲线 | 平均亮度 ≥0.20，p95 ≥0.55 |
| 4 | 颗粒减半（尤其 A7 序列） | grain 强度 | 暗部噪声 ≤7 |
| 5 | 白平衡门槛：跨场景 R/B 收进 1.15–1.35 | 夜景分支的色温锚 | 重跑 `originals_report.swift`，0 条 R/B 越界 |
| 6 | 序列同组曝光拉平（以 flash 帧为基准，ambient 提 0.3–0.5 EV） | `captureSequence` 后处理 | 同组亮度差 <0.10 |

## 6. 样张可用性

| 用途 | 结论 |
|---|---|
| 商店截图 | **不可用**（方向、肤色、N2 三项） |
| 社媒内容 | A8 / C1 室内自拍 2 张可用；街景要等方向修好 |
| 对比测试 | 可作为「问题样本」入库，但不能当基准 |

建议：修完 1–2 后，用同一台机重拍一组「白天窗边自拍 / 夜晚路口 / 车内仪表台 / 无闪夜景」四场景，再跑一次 `originals_report.swift`，R/B 与裁切全部过门槛后才拿去出商店图。
